# pm-hrm 项目规划与阶段交付

- **日期**：2026-10-10。
- **状态**：阶段规划待整体评审；D-000至D-022继续有效，人员方案A范围及账号关系已确认。交付批次及其余新增操作规则不自动成为已确认决策。
- **规划方法**：使用pm-execution outcome-roadmap，从用户结果倒推能力、依赖和阶段证据。
- **当前依据**：[产品总览](产品总览.md)、[已确认决策](产品探索/产品决策记录.md)、[产品输出审查](产品探索/历史记录/需求文档产品输出审查-2026-10-12.md)及工作区变更。当前检索未见应用源码或应用依赖清单，没有实现、测试或收益已验证证据。

## 一、目标与当前判断

**业务目标**：让技术部前端招聘的HR、职位用人负责人和实际面试官，在HRM中明确责任、完成招聘协作并追溯决策。飞书继续承担职位审批和发布，Boss直聘继续承担外部招聘沟通。

**项目目标**：验证AI能否主动完成问题识别、产品定义、实施交接、真实验收和反馈闭环。文档数量不是成功标准；用户不应承担提醒AI补人员概念、数据流、异常分支和验收的责任。

现有“补PRD→补故事→补测试”主要围绕产物展开。本次调整为“人员及权限可靠→招聘资料可管理→面试协作可完成→决策可追溯→试点价值有证据”，每一步都有依赖和退出条件。

| 现状 | 判断 | 规划处理 |
| --- | --- | --- |
| 招聘阶段、快照、评价、终止及关键异常已有规则 | 保留已有产品资产，不推倒重做 | 复用现有17条故事与35个场景；补齐对应局部缺口 |
| 人员身份与账号关系没有独立定义 | 基础概念和能力归属存在缺口 | 优先完成人员基础方案，再交接相关账号及责任指派功能 |
| 平台能力与招聘目录有混属 | 已补归属索引，但交互不完全 | 共用机制集中承载，业务规则留在招聘，按能力拆交付项 |
| 来源、安排字段、逾期面试和待办／已读仍不完整 | 对应功能不能由研发猜政策 | 纳入具名任务与局部决策，不泛化为全部开发阻塞 |
| 没有团队容量、交付期限及真实试点结果 | 当前无法承诺日期和收益 | 先按阶段排序，研发评估后补人力、工期和日历排期 |

## 二、产品结构与本期边界

| 层次 | 能力及归属 | 本期处理 |
| --- | --- | --- |
| 人员与组织基础 | 内部人员身份、部门关系；为账号和招聘指派提供人员引用 | D-022确认最小内部使用者范围及人员账号关系；其他操作仍待细化，不是完整员工档案模块 |
| 账号与权限 | 登录账号、账号可用状态、角色及授权判定 | 已有MVP能力；账号不是“这个人”的全部业务含义 |
| 平台共用能力 | 字典、工作台、站内消息、审计及授权回收入口 | 复用公共规范，业务触发来自招聘 |
| 招聘管理 | 职位、应聘资料、筛选、邀约、模板、场次、评价、招聘决策 | 本期唯一完整业务闭环，内部能力见[落地映射](产品总览.md#capability-mapping) |
| 后续业务 | 员工档案、入职、转正、调岗、离职、薪酬、考勤及绩效 | 当前不自动纳入；绩效为已有后续方向，其他内容先验证需求和优先级 |

推荐操作入口：工作台、招聘管理、人员与组织、平台设置。人员与组织承载人员、账号和角色管理的关联视图；招聘管理内提供职位及候选人入口，面试和评价可由详情及工作台进入。入口名称与是否拆成独立菜单待交互评审，不因能力划分强制增加菜单。

### 人员基础的最小方案（方案A范围及关系已确认）

用户已明确HR和面试官首先是独立人员，再通过角色及职位区分。D-022确认仅管理内部使用者，每人一份人员信息、一个账号及管理员统一维护；具体管理动作仍需补齐。

| 概念 | 推荐定义 | 明确不混用的内容 |
| --- | --- | --- |
| 内部人员 | 对系统内招聘参与人的统一身份引用，姓名仅用于显示；改名、改邮箱不改变历史人员关联 | 不将HR和面试官各维护一份人员；不把同名认定为同人 |
| 账号 | 与人员关联的登录入口及认证状态；D-022确认本期一人一个账号，创建人员及账号可在同一表单完成 | 逻辑分离不要求用户重复录入，也不预定数据库拆表 |
| 角色 | 账号可用时具备的HR成员、面试官、管理员等权限资格，可多选 | 角色不是人员身份；用人负责人不是额外账号角色 |
| 组织与岗位 | 部门是组织归属；员工岗位属于自身任职信息，如本期没有使用场景则暂不新增岗位维护 | 部门或员工岗位不等于正在招聘的职位，也不自动授权 |
| 责任指派 | 人员对某招聘职位／场次承担的责任，操作同时满足有效账号、所需角色及业务条件 | 身份、资格和责任分别判断，历史参与不等于当前访问权 |

推荐一期只维护招聘参与人必需的姓名、邮箱、部门、账号及角色关联，不收集身份证、合同、薪资等资料。人员重复识别、邮箱变更、账号禁用与重新启用、角色移除和任务交接必须有明确动作及结果。

人员管理的查看、创建、修改、删除／停用、恢复、下载和导出权限应逐项评审，不能将招聘HR全局业务权限直接套用到人员资料。建议管理员维护基础资料，HR业务角色不因此获得人员管理权限；新范围需确认后回写公共规范。人员及账号生命周期应分开记录；账号禁用沿用现有规则，不代表已建设员工离职流程。历史引用不得因删除人员而丢失。

**最小验证**：用同一人兼任HR和面试官、变更邮箱、移除角色、禁用账号、替换职位负责人五个案例走查。验收草案：每人身份引用一致；授权按当前有效条件判断；历史作者不变；未完成责任可定位到明确交接入口。任一案例需要新建重复人员或无法找到未完成责任，即退回人员及指派规则评审。

确认后，平台说明承载能力与交互，公共规范维护共性身份／生命周期规则，招聘只引用人员及维护业务指派；只有确实决定建设独立人员业务模块时，才按项目规范建立四份模块文档并更新总览。

### 字段级交接门禁

字段级定义在P0按人员基础、账号角色与指派、职位及应聘资料、筛选邀约、模板场次、评价决策、平台聚合治理的依赖顺序逐组完成，清单与完成标准见[产品需求TODO](TODO.md)。已有字段表需复核补齐，不仅处理几个已发现的缺失字段。涉及业务含义、来源、必填、修改权限及状态条件的关键未决项，在对应功能技术设计前收口；数据库和接口表达留给后续技术设计。

## 五、决策、排期与变更管理

**优先范围选择**：推荐本期只补“招聘参与人的最小人员基础＋现有招聘MVP”，而不是同时建设全量员工管理。它能解决身份及责任问题，并维持招聘试点的清晰验证对象。完整员工管理会引入更多数据、权限和生命周期，须另做发现及范围评审。

决策顺序：先确认最小人员范围和账号关系，再评审来源／安排字段、逾期及展示规则，最后确认M-004统计方案。产品先提供推荐、理由、案例和差异，只向业务负责人提出仍会改变范围或行为的必要问题；既有D-020／021不重新开启。

资源与排期输入：业务决策负责人、研发及测试可投入容量、期望试点窗口、是否存在外部硬期限。研发按交付批次估算后，再补每批负责人的姓名、工期、依赖及缓冲；日期变化时保留取舍原因，不能用“多写文档”代替实际排期。

每个交付项使用：目标用户与结果、范围、前置决策、验收入口、负责人、当前状态、阻塞原因。状态采用待决策／可评审／可实施／实施中／待验收／已验收，当前不得将整包标为可实施。

新增需求依次检查范围、依赖、状态、权限、数据、异常、指标和验收影响；产品维护决策及权威需求，研发评估成本，业务负责人取舍。批次冻结后不能私自追加员工档案、Offer、同步API或外部通知。

## 六、试点验证与扩展条件

沿用[指标与试点基线](指标与试点基线.md)，不另造相冲突的目标。M-005提醒正确命中、M-006闭环可追溯、M-007越权阻断按既有100%门槛验收；M-001／002比较人工基线，M-003及确认后的M-004观察后续周期。

人员及角色五例走查为新增验证草案，需确认后纳入验收。用脱敏数据先完成正常闭环和关键异常验证，再按既有发布评审进入真实试点。若关键状态与决策不一致、通知错对象或越权泄露，修复对应问题后再复验；不能用正常链路成功抵消。

效果扩展依赖真实证据：技术部前端样本和观察窗口记录完整、权限与闭环门槛满足、耗时和协作问题可解释、业务参与者确认可使用。样本不足不宣称效率改善。若流程有效但收益不明确，继续有限试点；若基础身份／权限不可靠，先修基础再扩展。

后续优先评估其他招聘岗位；飞书／Boss集成、员工管理与绩效各自提出问题证据、数据边界和最小方案再排序，不预先承诺全部建设。

## 七、AI主动交付要求

产品阶段由AI负责维护缺口、推荐方案、权威文档、图示、故事及验收关联；实施前主动报告对应功能是否可实施，而非等待用户问“人员有没有”“图有没有”。每次交接需说明已完成事项、局部未决项、证据和下一步。

新增质量检查：所有涉及“人”的功能先明确人员身份、账号、角色、组织归属、业务指派与历史作者分别是什么；检查同人多角色、改名／改邮箱、禁用、角色移除、任务交接和历史追溯。概念图存在但案例预期不唯一时，不判定为已解耦。

本轮完成的是可评审的规划与工作包，不是人员新规则的确认、项目日历排期或真实实施验收。

# 权限、审计与数据生命周期规范

- **适用范围**：HRM 全部模块，包括工作台、招聘管理和绩效管理。
- **状态**：公共基线，模块特有规则需要在模块 PRD 中补充。
- **维护原则**：本文件定义跨模块共性要求；具体角色、数据范围和操作权限由模块文档结合本基线落地。

## 一、数据敏感性

员工、候选人、简历、面试评价、绩效目标和评价记录都属于人事敏感数据。身份证件、合同、薪酬等更高敏感数据进入系统前，必须重新评审访问范围、审计要求和生命周期。

## 二、账号与组织基线

- HRM 使用独立账号体系和账号密码登录，不默认复用外部平台组织架构。
- 管理员负责创建、禁用和恢复用户，以及维护部门、业务角色和组织关系。
- 管理员创建用户时设置临时初始密码；用户首次登录必须修改密码后才能继续使用系统。
- 管理员重置密码后，用户下次登录必须再次修改；创建和重置操作必须写入审计记录。
- 用户唯一身份默认以唯一邮箱为主，姓名作为展示字段；模块可以增加业务唯一标识。
- 部门变更完成后，新权限立即生效；离职用户禁止登录，但历史记录保留原操作人和必要的历史关系。
- 一个用户可以绑定多个业务角色，实际业务权限按角色合并计算。
- 平台管理员权限不自动转化为全部业务数据权限；管理权限和数据权限必须分开控制。

## 三、权限模型基线

- 权限至少拆分为查看、创建、修改、删除、恢复、下载、导出和管理配置等操作级别。
- 数据范围至少支持全局、部门、职位/项目、本人负责和具体任务/记录等层级。
- 前端隐藏按钮不能作为权限控制；每个敏感操作都必须在服务端再次校验用户身份、业务角色、数据范围和记录状态。
- 多角色用户执行操作时，系统记录实际用户、作用角色、目标记录、操作时间和操作结果。
- 用户失去权限后，不能继续访问新数据；历史数据是否保留访问权必须由对应模块明确说明。
- 模块 PRD 必须提供角色、数据范围和操作权限矩阵，不得只描述页面可见性。

### 3.1 角色、权限与责任指派的定义

| 概念 | 产品定义 | 描述要求 |
| --- | --- | --- |
| 用户 | 实际登录并执行操作的自然人账号 | 操作始终归属于实际用户，不能以角色或责任人替代操作人 |
| 角色 | 围绕一组业务职责定义的权限集合 | 明确职责、允许操作和禁止事项；平台管理角色与业务角色分别定义 |
| 操作权限 | 对某类业务对象执行某个动作的授权 | 按“对象＋动作”描述，如候选人查看、简历下载、面试评价修改 |
| 数据范围 | 某项操作允许作用的记录集合 | 分别明确查看范围与操作范围，不因可查看而允许修改 |
| 责任指派 | 用户与具体职位、项目、任务或记录的责任关系 | 明确主责、参与人、资格要求及指派变更影响；模块可定义由有效角色与责任指派共同授予的记录级权限，指派本身不能绕过所需资格及状态条件 |
| 业务条件 | 操作成立所需的状态和前置事实 | 明确当前状态、允许动作及前置条件；不能只列出角色名称 |

### 3.2 授权判定与多角色合并

- 每次操作必须满足账号可用，并在至少一个授权角色下完整满足该操作的数据范围、适用的责任指派和业务条件。
- 多角色权限合并的是各角色完整授权结果，不能把角色甲的数据范围与角色乙的操作权限拼接成新的授权。例如仅在本人任务内可修改的角色，不因另一个角色可全局查看而获得全局修改权。
- 未明确授权的操作默认拒绝；待确认的权限范围不能视为已经授权。模块需要区分“允许”“禁止”和“待确认”，并将待确认项列入需求评审。
- 模块可以将负责人定义为记录级责任身份；此时账号角色、负责人指派和具体任务参与分别判断，不必再维护同名账号角色，也不能因主责身份自动取得所有子任务参与权。
- 责任指派条件只适用于明确依赖该关系的操作；拥有全局查看权限的角色不要求被逐条指派，模块应逐项说明。
- 保留历史操作人、历史角色或责任关系用于追溯，不代表保留当前访问权限；每次访问仍按当前有效授权判断。

### 3.3 PRD 表述与验收格式

- 角色表说明“职责、数据范围、允许操作、禁止事项”；操作矩阵说明“业务对象、动作、可执行角色、适用数据范围或指派关系、状态条件”。
- 需求采用“具备某角色的用户，在某数据范围及责任关系内，满足某业务条件时，可以对某对象执行某操作”的表述。
- 每项授权至少验收允许操作、缺少角色、超出数据范围、不满足指派关系和状态条件等适用场景；角色、部门及指派变更后，重新验证当前权限。
- 页面入口、列表、详情、搜索、工作台和附件访问遵循同一授权范围；无权限反馈不能泄露目标记录的敏感内容。

## 四、敏感数据访问

- 查看、修改、下载和导出敏感数据分别授权，不因拥有查看权限自动获得下载或导出权限。
- 附件访问必须经过权限校验，不能仅凭不可过期的公开链接访问。
- 敏感数据在列表、日志、错误信息和通知中按最小必要原则展示。
- 密码、令牌、完整附件路径和其他认证信息不能写入普通日志。
- 模块如需批量导出，必须明确角色、数据范围、字段范围、审批要求、文件有效期和导出审计。

### 4.1 产品文档与参考资料脱敏

- 产品需求、示例、流程矩阵及参考截图使用匿名编号或业务身份替代真实姓名，文档与图片须同时脱敏，不在仓库保存明文姓名映射。
- 图片采用覆盖并重新编码的方式去除原姓名像素，不用可撤销图层或模糊作为脱敏结果；不附带未脱敏原图。
- 脱敏不等于加密。确需可还原的人员名单时，原始名单及映射应在另行授权的受控存储中加密保存，密钥与数据分开管理；不把密钥、原始名单或映射写入产品文档及仓库。
- 文档匿名编号仅用于示例关联，不作为系统账号、职位负责人或面试官授权依据。

## 五、软删除与数据生命周期

- 业务数据默认采用软删除，不直接物理删除主记录、附件引用和过程记录。
- 软删除记录默认不出现在正常列表、搜索和统计中；恢复入口只提供给管理员或模块明确授权的角色。
- 删除必须记录操作人、操作时间、删除原因和原记录标识。
- 恢复必须记录恢复人、恢复时间、恢复原因和恢复前后状态。
- 审计记录采用追加方式保存，不提供普通业务删除入口，也不能无痕修改。
- 数据保留期限、主动删除、归档和法律保留要求必须由模块或公司制度单独确认；未确认前不得自动清理敏感数据。

## 六、审计基线

至少审计以下行为：

- 登录、登出、密码创建、重置和修改。
- 用户、部门、角色和权限配置变更。
- 敏感数据查看、修改、下载和导出。
- 业务记录创建、修改、状态变更、软删除、恢复和合并。
- 权限拒绝、校验失败和高风险操作失败。

审计记录至少包含操作者、作用角色、操作时间、目标记录、操作类型、结果和必要的变更摘要；依赖责任指派授权时，还应记录相应职位／任务及责任身份。审计内容不得包含密码等认证秘密。

## 七、模块落地要求

每个模块的 PRD 需要补充：

1. 模块角色及角色之间的职责边界。
2. 数据范围和操作权限矩阵。
3. 模块敏感数据类型及其查看、下载、导出规则。
4. 删除、恢复、归档和保留规则。
5. 模块特有的审计事件。

招聘管理模块的候选人告警、候选人去重、职位关闭和简历处理规则属于模块需求，详见[招聘管理模块范围说明](../模块/招聘管理/范围说明.md)。

# 产品经理工作与需求质量检查

## 目标与责任

AI负责识别当前阶段、选择并应用合适技能、主动发现遗漏、提出建议、维护一致性及给出验证依据。用户负责提供真实业务信息和作出必要业务取舍，不承担提醒AI补齐专业产物的工作。

技能是方法来源；项目规则约束执行方式；交付证据用于核查结果。本文件定义质量检查，不扩展业务范围，不替代已确认决策、公共规范、模块需求和现有阶段门禁。

## 正式交付的主动复审流程

用户反馈一个问题时，先判断它属于需求规则、受众边界、正文结构还是导出缺陷，再检索整包同类问题与关联规则。用户示例用于定位问题类别，不能作为本次检查的全部范围。定位时先确认实际路径、章节和交付版本，不凭摘录判断output已有残留。

### 检查与整改顺序

1. 读取当前差异、需求源与实际output，明确读者、用途及本次影响；既定文件结构不重新讨论。
2. 按文档用途复审：入口负责导航；总览负责目标、范围与系统关系；PRD负责可执行需求；公共规范负责共用约束；验收负责步骤与预期；试点配套负责效果验证。内部确认过程、编写方法、来源资料整理经过留在内部。
3. 按页面及业务单元连续检查：输入、资格、动作、结果、失败、返回和历史能否得到唯一预期。索引或“按某规则”只能定位，不能代替本页的实际业务条件。
4. 将长段落按并列条件或操作整理，区分页面、字段、状态与例外。检查相邻及同名章节是否重复定义；图示重复表达同一规则时注明判定用途，图文条件须一致。不机械追求段落字数、表格数量或九章齐全。
5. 修正权威正文，再导出实际交付文件；抽象决策名串、未知编号兜底、空引用或断句必须重写完整语句，不能仅删除词语。保留必要业务原因、范围限制和真实实施依赖。
6. 运行导出及预检，处理全部确定性错误，逐条判断阅读提示；最后对本次主题及关联页面推演正常、条件不足、授权拒绝和适用异常。规则变更同时核对字段、图示、追踪和验收；新业务取舍由用户确认。

### 自动预检与语义复审的分工

运行 `python3 scripts/export_product_delivery.py` 时自动执行写入前检查；确定性错误会阻止本次生成文件写入。`python3 scripts/check_product_delivery.py` 可独立检查实际交付文件及生成一致性。

| 自动发现／阻断 | 产品经理仍须判断 |
| --- | --- |
| 内部编号／过程引用、已知拼接句、空链接 | 当前业务条件是否完整，表达是否专业，来源信息是否应进入正式正文 |
| 包外或失效引用、失效锚点、重复显式锚点 | 引用是否必要，是否迫使读者拼接功能 |
| 表格列数、代码块、入口版本和生成一致性 | 字段、页面、角色、状态及异常能否得到唯一结果 |
| 未知决策和多项决策名的兜底输出 | 如何以实际业务规则改写；不能让脚本自动决定业务含义 |
| 长段落和同名业务章节提示 | 是否需要合并、改名、拆段或保留图文两种表达 |

无自动错误不代表正文合格。复审记录说明逐份发现、实际整改、案例预期及剩余依赖；只有完成范围内的正文复核才报告完成，不用引用数量或导出成功证明“专业性已通过”。检查记录留内部，不增加开发必读文件。

## 标准需求交付结构与正文门禁

本节是本项目后续模块需求输出的必查标准。产品技能模板提供方法，正式交付以目标读者和本节为准；不能直接沿用探索模板，或靠索引补偿正文分散。它约束需求表达，不新增业务政策。

### 0. 整套交付的适用标准

审查范围为交付入口、产品项目总览、每个模块PRD、验收附件及入口明确的必读／按能力必读配套，不能只审查模块PRD。产品过程资料不因位于同一仓库而自动成为交付正文。

| 文档 | 面向读者必须解决的问题 | 组织原则 |
| --- | --- | --- |
| 交付入口 | 从哪里读、顺序是什么、哪些配套必读、当前交付状态 | 简洁导航与阅读职责，不展示讨论历史或维护日志 |
| 产品项目总览 | 产品目标、边界、全局架构、角色协作、数据权威与实施依赖 | 按系统视角组织，能力地图只说明业务职责，不替代页面定义，也不套CRUD页面模板 |
| 模块／平台页面需求 | 每个实际页面显示什么、谁能操作、输入和结果是什么 | 业务组内按页面独立定义，按钮归页，基础字段与共用机制可精准引用 |
| 公共规则／字段配套 | 多页面共用的数据含义、校验、授权及生命周期是什么 | 按规则或对象组织，不机械拆成页面；不得含当前结论之外的待确认历史或抽象规则名拼接句 |
| 验收附件 | 针对哪个当前页面／规则，怎样执行并判断结果 | 保留可用的追踪编号，需求位置精确到章节；版本与正文变更同步，编号不代替预期 |
| 指标与试点依据 | 怎么统计、由谁采集、样本不足如何处理、何时判断达标 | 区分确认口径与真实采集值，不把文档覆盖当效果验证 |

逐份核对版本日期、读者、术语、按钮文案、图文一致、引用及实际未决项。新业务规则先确认；已确认信息的命名、归位、引用及阅读问题直接修复。逐页缺口必须明确记录，不能以“整套审查已执行”宣称“整套交付已通过”。

### 1. 核心PRD的默认章节

| 章节 | 必须表达的信息 |
| --- | --- |
| 1. 文档信息 | 产品／模块、版本、明确的交接职责、状态、更新时间；版本变化及实施影响 |
| 2. 目标与范围 | 业务问题、目标用户、价值、成功指标、本期包含／排除及外部边界 |
| 3. 角色与权限 | 身份与责任区别、数据范围、动作授权及资格；共性机制准确引用 |
| 4. 业务概览 | 术语、对象关系、端到端主链、角色交接及关键状态 |
| 5. 功能需求 | 按业务对象分组，组内按列表、详情、表单等实际阅读单元定义字段、动作、状态、异常及验收；相近新增／编辑共用字段，入口、初始化／回填、保存及结果归对应动作 |
| 6. 跨功能异常 | 只放跨功能共同处理；各功能特有异常留在对应功能，不重复维护 |
| 7. 数据与系统依赖 | 来源与权威归属、关联、历史、外部交接及所需平台能力 |
| 8. 非功能要求 | 安全、审计、性能、兼容性及已确认运行目标；实施验证按计划及验收记录承接 |
| 9. 验收与交付条件 | 可判定验收、明确的实施依赖和发布条件；详细步骤可入附件 |

统一采用中文标题、稳定章节与锚点。简单模块可合并相邻章节，不适用项说明原因；不能删去适用内容，也不为模板填造目标、责任人或指标。版本记录放在顶部；有文档信息时紧随其后。不因正文变长另拆字段／按钮／异常文件让读者拼接功能。

影响本期行为或验收的未决选择先在内部确认，确认后再纳入正式定义；未解决的部分不能声明已准备好交付。正式定义不因需求尚未实现而省略已确认的实施与验证要求。

### 2. 每项功能的连续阅读单元

业务功能组内按页面定义，各页面可以独立阅读：目标角色与价值→入口与前置条件→页面／字段（业务含义、必填、默认、可编辑、校验）→操作与授权→成功反馈及数据／状态／责任变化→失败、条件不足与异常→验收摘要。读者应能回答“谁在什么条件下输入什么，执行什么，系统改变什么，失败如何处理”。

标题采用“业务对象＋动作／判定内容”，区分日常编辑、计划调整、错误修正、状态变更和责任变更；方案代号及确认标签不作为功能名。正文按“执行人、适用记录、入口、输入、校验、结果、失败”表达，禁止自动替换决策编号后拼接抽象规则名形成句子。

页面说明直接写展示内容、可编辑内容、动作、成功结果及失败处理；禁止用US／TS／RB编号串联代替规则，详细追踪放验收附件；内部源可保留编号，面向读者的PRD不显示按钮编号及故事／测试编号列，也不在正文拼接工程追踪编号。

页面需求必须明确页面名称、区域、按钮名称和触发入口（打开表单／确认框／跳转），不能仅写“详情”或只罗列业务动作。具体动作授权归对应页面；角色章说明整体范围和判定方式，不另维护一份重复动作政策。工作台跳转到业务操作区，平台恢复／配置入口与招聘敏感详情区分。

按钮的显示／禁用、提交复核和拒绝反馈必须在所属页面明确。整体授权章说明角色范围和判定机制；页面定义实际资格、责任及状态条件，不用“见权限章节”代替准入。共用字段含义、状态机和授权机制只维护一处，页面写明实际展示、编辑与操作要求；跨页面一致性在变更时校验，不把减少重复置于页面可独立阅读之前。

概览保留端到端图；具体场次、字段及异常图放到相关功能旁。选择数据流、泳道、状态、概念关系或决策表回答不同问题，按既有图表规范验证，不机械一图覆盖全部信息。

### 2.1 页面、按钮、表单命名与页面独立性

本项目统一以下命名与组织方式，后续模块产出及现有需求重组均须执行。

| 概念 | 命名标准 | 职位示例 |
| --- | --- | --- |
| 列表页面 | 业务对象＋列表页 | 职位列表页 |
| 新增按钮 | 新增；所在页面对象明确时不重复对象名 | 职位列表页的“新增” |
| 新增／编辑共用页面 | 业务对象＋新增／编辑页；运行时标题按模式显示 | 职位新增／编辑页，标题“新增职位”或“编辑职位” |
| 详情页面 | 业务对象＋详情页 | 职位详情页 |
| 编辑按钮 | 编辑；多个独立编辑区域时明确编辑目标 | 职位详情页的“编辑” |
| 编辑页面 | 业务对象＋编辑页 | 职位编辑页 |
| 页面输入区域 | 业务对象／内容＋信息表单 | 职位信息表单 |
| 表单提交与退出 | 保存、取消；特殊业务动作使用明确动作名 | 保存、取消、关闭招聘、恢复招聘 |

“建档”可以说明建立业务记录，不作为职位新增按钮或新增页面名称；“表单”指输入区域，不代替页面名称。“新增”“编辑”不得用于掩盖关闭、恢复、指派等有独立状态或权限影响的业务动作。

独立页、弹窗、抽屉须明确实际承载方式。采用独立页时，可用“职位新增／编辑页”统一描述两种模式；确有独立流程时使用“职位新增页／职位编辑页”；确实采用弹窗或抽屉时注明“新增职位弹窗／编辑职位抽屉”，不把三者混称为页面，不因统一命名擅自新增页面或改变已确认导航。具体承载方式未定时列为设计待落实项，不伪装成已定交互。

功能章节按实际阅读单元分开。例如“职位管理”下写“职位列表页”“职位新增／编辑页”“职位详情页”。新增与编辑的字段及布局相近时，共用字段表维护一次，入口、资格及初始化／回填归对应按钮，默认值、只读／隐藏字段及校验归字段表，创建／更新、确认、结果与返回归保存按钮；不另用差异表重复已有定义；不机械拆成两份重复页面定义。差异较大且确有独立流程时才分别定义，无需为每个页面增加独立文件。每个单元至少明确：

- 目标与使用角色、进入方式、离开或返回位置。
- 页面区域、展示字段及只读／可编辑范围；列表还须明确适用的查询、筛选、排序、分页和空状态，不适用时说明。
- 本页按钮的位置、名称、显示／可用条件，以及点击后跳转、打开表单或确认框的结果。
- 输入、校验、保存成功与失败反馈、取消行为及适用异常。
- 角色、数据范围、责任和状态限制及本页验收预期。

仅需实现列表时应能从列表章节获得完整列表需求；详情同理。实现新增或编辑时在共用表单章节内即可理解共同字段与该模式差异。禁止把列表、详情及其他不同用途页面的按钮混成一个操作总表，让读者按“页面／区域”列自行拆分。跨页入口写清目标页，例如“职位列表页点击新增→进入职位新增页→填写职位信息→点击保存”，保存及取消后的返回位置须在对应页面定义。

复用对象字段含义、字典、状态机、授权及审计机制；分别定义字段在各页的展示和交互。列表中的招聘状态展示、详情中的状态说明和关闭按钮是不同页面需求，不能只写“复用详情”。同一动作有多个入口时，每页写明入口与目标，提交规则可引用唯一操作定义，不能省略本页反馈。

完成判据：页面名称、按钮文案、表单名称和实际承载方式在PRD、图示、原型及验收中一致；每页独立回答显示什么、能做什么、点击后发生什么。发现命名或页面混写直接整改，规则或交互方案变化另按确认流程处理。

### 2.2 页面需求表头与用法规范

适用于所有本期及后续模块PRD的页面、弹窗和抽屉。四类标题统一为“按钮”“输入字段”“筛选项”“展示字段”；可在业务标题中说明对象和区域，表头不加对象前缀、不合并信息维度。内部按钮编号及场景追踪保留在源或验收附件，正式页面表不展示。对象关系、系统事实、状态流转和区域概览表按其用途组织，不强行套页面输入表。

#### 固定表头

| 类型 | 固定列名与顺序 |
| --- | --- |
| 按钮 | 按钮名称、所在位置、操作权限、前置条件、点击行为、确认要求、成功结果、异常反馈 |
| 输入字段 | 字段名称、业务含义、数据类型、控件类型、取值来源、默认值、必填条件、校验规则、修改与历史 |
| 筛选项 | 字段名称、数据类型、控件类型、取值来源、默认值、筛选规则 |
| 展示字段 | 字段名称、数据类型、取值来源、展示规则、空值展示、交互说明 |

#### 按钮列职责

| 列名 | 填写要求 |
| --- | --- |
| 按钮名称 | 页面实际文案，一行一个动作；保存、取消、关闭与恢复分别定义 |
| 所在位置 | 实际页面／区域，如人员详情页／角色区；不能只写“详情” |
| 操作权限 | 所需动作及查看权限；基础登录操作可写当前有效登录用户，不凭预置角色名称授权 |
| 前置条件 | 当前记录范围、实际责任、状态、版本及前置事实；与权限同时成立 |
| 点击行为 | 点击即发生的动作：跳转、打开弹窗、提交、查询；注明目标载体 |
| 确认要求 | 输入原因、核对影响、二次确认等；无确认写“无需额外确认” |
| 成功结果 | 成功后数据、状态、责任及历史变化，提示、关闭、刷新和返回位置；与点击行为区分 |
| 异常反馈 | 条件不足、失权、校验失败、并发、提交中或等待的反馈，是否写入、保留输入及可采取动作；无特殊情况写“不适用”或准确引用公共反馈 |

#### 字段列职责

| 列名 | 填写要求 |
| --- | --- |
| 字段名称 | 界面实际名称；不同区域通过标题定位，不改为“资料字段名”等表头 |
| 业务含义 | 字段记录什么业务事实；不混入控件或保存按钮行为 |
| 数据类型 | 产品数据类别，如文本、整数、布尔、枚举、日期时间、对象引用或集合；不是数据库类型、输入控件或展示样式 |
| 控件类型 | 文本输入框、单选下拉框、多选框、日期选择器、上传控件或只读等实际输入方式 |
| 取值来源 | 人工输入、字典、关联对象、系统事件或推导来源；涉及选项时写清可选集合和授权范围。对比表在单元格区分本次录入与已有记录 |
| 默认值 | 输入字段指新增或首次打开的默认值，筛选项指首次进入及重置值；无默认写“无”，仅编辑写“不适用（仅编辑）”。编辑回填归修改与历史；占位文字不是默认值 |
| 必填条件 | 是、否或明确的条件必填；不只写“按情况” |
| 校验规则 | 格式、长度、唯一性、跨字段和关联资格；引用公共格式，同时就地定义本页特有约束 |
| 修改与历史 | 当前值／版本回填、可改／只读条件、修改限制及证据保留；保存整体后果归按钮 |
| 筛选规则 | 包含或精确匹配、区间边界、条件组合及查询／重置影响；本页特殊规则就地定义，共用分页保持唯一维护 |
| 展示规则 | 标签、链接、时间格式、截断、脱敏及当前值／快照选择；不以“文本链接／状态标签”代替数据类型 |
| 空值展示 | 实际占位文案，如“—”“未填写”；与空列表、加载失败区分，展示占位不回写业务数据 |
| 交互说明 | 只读、点击跳转、展开或预览及目标；无交互写“只读”，下载及变更动作归按钮表 |

#### 组织与复核

有筛选区按筛选项→按钮→展示字段组织；无筛选区按按钮→输入／展示字段组织。同一页按实际区域分别定义，输入及展示没有发生时不制造空表。新增／编辑共用字段，默认值与回填分开；按钮资格与前置条件分开，打开弹窗与成功保存分开。复核至少推演筛选后重置、空值展示、编辑回填、保存失败及失权提交，不以表头相同代替业务语义一致。

行业参考：[W3C表单说明](https://www.w3.org/WAI/tutorials/forms/instructions/)强调清楚标识必填、数据格式和输入说明，且占位文字不能代替字段标签。它提供交互质量依据，不规定PRD表头；本项目的四类名称、列顺序及职责为项目统一约定。

版本变更记录统一位于文档顶部：有“文档信息”章节时，紧随其后；无该章节时，置于标题之后、业务正文之前。版本、日期、变更内容及影响范围在该处集中表达，模板和生成输出采用相同顺序。

### 3. 链接边界与交付依赖

- 可使用目录锚点、共享规则及详细验收引用；链接用于定位，不能代替本模块核心业务定义。
- 正式输出保留入口、主要章节、公共规则和验收场景的必要定位；同一章节只保留一个有效定位，正文相邻内容用普通文字引用。旧标题、内部决策及重复兼容锚点仅留在内部源，导出时整包迁移引用并移除未使用标识；不删业务定义或验收场景以减少跳转。
- “PRD G.1”“场次字段”等引用须到相应章节锚点，禁止用整份自身PRD链接冒充具体章节定位。移动章节后同步正文、目录及外部引用，保留或迁移稳定锚点。
- 共享正文保持唯一权威；交付入口明确必读配套与按需配套、服务哪项能力。同仓库交付可精准引用共享正文；若需要独立包，则从权威源生成配套并核对同步，不能手工复制政策或留下不可访问链接。
- 交付不要求读者理解内部讨论、D编号、收口过程、文档归属或AI补充记录。“字段交接补充”“收口入口”等补丁正文须归入相关功能；只保留必要业务原因和真实依赖。

### 3.1 本期能力与正式输出覆盖

正式交付先对照已确认的MVP范围、系统能力归属和实际页面，建立“能力／页面→正式PRD章节→验收依据”的覆盖关系。检查包括基础资料、平台支撑和业务模块，不因能力属于平台、已有内部字段文件或被业务模块引用就默认已交付。新增本期能力或页面后同步检查此关系、输出入口与依赖引用。

## 一、每次任务的工作步骤

1. **定位阶段**：读取Git变更和相关权威文档，明确本次目标、范围、已确认结论及尚缺证据。
2. **选择方法**：按下表读取主技能，需要时组合一种评审方法；遵循项目文档路由，不另造平行权威文档。
3. **主动判断**：指出影响当前目标的缺口及建议，不只照用户描述补文字；区分可直接完善的表达与需要业务决策的规则。
4. **完成产物**：对已授权范围直接推进，更新关联文档、图示和验收；需要决策时先准备可评估的具体方案，继续完成不依赖该决策的工作。
5. **核查交付**：对照相关质量维度检查，报告证据、剩余事项及推荐下一步。新证据或规则变化时重新检查，不重复执行无变化的检查。

| 工作阶段或问题 | 优先方法 | 要形成的判断 |
| --- | --- | --- |
| 发现问题与用户需求 | pm-product-discovery 的 interview-script、identify-assumptions、prioritize-assumptions、brainstorm-experiments 等对应技能 | 哪个问题值得做，证据是什么，如何便宜地验证 |
| 定位与范围取舍 | pm-product-strategy 的 product-strategy、value-proposition；必要时 pm-market-research | 为谁解决什么，边界和取舍是什么 |
| 需求细化与研发交接 | pm-execution 的 create-prd、user-stories、test-scenarios 按任务选择 | 流程、状态、数据、权限和验收是否足以实施 |
| 关键假设与方案评审 | pm-execution 的 strategy-red-team 或 pre-mortem | 什么事实会推翻方案，如何最小验证 |
| 成功指标与试点 | pm-data-analytics；指标定义采用 pm-marketing-growth:north-star-metric 或 pm-product-discovery:metrics-dashboard 按实际需要 | 用什么证据评价效果，不虚构基线或目标 |
| 实现审查与发布交接 | pm-ai-shipping 的 intended-vs-implemented、code-review、shipping-artifacts 按实际需要 | 需求是否落实、权限是否有效、哪些测试实际执行 |

技能名称由AI选择，用户无需手动触发。主技能模板不是完整性上限；例如PRD模板没有强制图示章节，仍须按复杂度表达数据、角色交接和异常路径。实现阶段的技术审查产物不得提前伪装为已有实现证据。

## 二、需求质量检查

以下维度按任务和阶段适用。可复用已有文档并链接证据，不要求每次生成所有产物；不适用项写明项目原因。结论使用“已覆盖／部分覆盖／缺失／不适用”，不能用文档存在代替内容检查。

| 维度 | 必须能回答的问题 | 主要证据位置 |
| --- | --- | --- |
| 用户与问题 | 谁遇到什么问题，事实、假设及优先级是什么？ | 产品发现、范围说明、PRD目标 |
| 价值与范围 | 为什么做、为何现在做、本期交付和外部边界是什么？ | 产品决策、产品总览、模块范围 |
| 业务架构与全局数据 | 系统由哪些业务能力组成，数据从哪里来，谁拥有权威状态，如何交接？ | 产品总览 |
| 模块流程与责任 | 角色如何交接，动作前置条件、成功结果和数据变化是什么？ | PRD、模块图示、最小配置 |
| 状态与异常 | 正常推进、等待、失败、取消、重试、跳过、终止、恢复各如何处理？ | 状态／异常图、决策、测试场景 |
| 数据与历史 | 对象如何关联，合并、版本、人员变更与替代记录如何保留证据？ | 模块对象关系、PRD数据规则 |
| 权限与治理 | 各动作的角色、范围、责任关系及状态门槛是什么，敏感操作如何治理？ | 公共规范、模块操作矩阵及拒绝场景 |
| 页面与交互 | 操作入口、关键按钮、空状态、等待、错误和确认反馈是否清楚？ | PRD交互、最小配置；需要时补原型 |
| 指标与验证 | 成功如何衡量，基线和目标来自哪里，验证假设需要什么最小证据？ | 指标基线、实验和试点记录 |
| 追踪与交付 | 决策、PRD、图、故事和场景是否一致，测试是已设计还是已执行？ | 需求追踪矩阵、执行结果 |

跨文档一致性检查应检索变更主题及旧说法，例如“待确认、自动淘汰、终面、CTO、权限、合并”。若旧记录保留用于追溯，应明确最新权威口径；当前导航和交付摘要不能继续把已确认规则写成待确认。

## 三、阶段结论与证据边界

- **需求可评审**：关键视图与规则已覆盖，未确认项显式列出，并给出建议、影响和验证方式。
- **需求可进入对应功能实施**：该功能所需关键业务决策已确认，验收可执行；未确认项不能以实现默认行为悄悄落地。局部缺口只影响对应功能，不自动阻断全部MVP。
- **功能已验收**：有真实执行结果及必要的日志／截图／测试证据；场景编号存在不代表通过。
- **可发布／可扩展**：满足既有发布门槛，具备必要的试点结果、责任人及未解决事项处置记录；不得因文档完善而宣称产品效果已验证。

重要阶段交付采用简短记录：本次主动发现什么、直接修复什么、哪项决策仍缺失、证据是什么、推荐下一步。链接可追溯到具体章节，避免泛泛“已检查”。

### 优先验证的三项判断

按影响与验证成本排序，未有数据支持时不编造概率或分数。

1. **合并规则足以实施**：保留主记录与旧证据能保证可追溯，这是已有方案的优点。但如果两条应聘记录分处面试中／待决策、或一条已淘汰，合并后的阶段和任务归属可能被研发自行推断。最小验证：用“待筛选＋待筛选、初筛＋面试中、淘汰＋待筛选”三组案例确认主记录阶段、活动任务、提醒及终止约束。判据：任一案例无法给出唯一预期，就不能将合并功能判定为可实施。推荐方案草案：先限制为均未进入流程的重复记录合并；已有流程记录只建立关联并保留独立流程。此建议改变现有合并范围，须业务确认后更新D-018相关规则；其他功能继续推进。

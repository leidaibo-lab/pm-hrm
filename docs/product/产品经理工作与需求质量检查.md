# 产品经理工作与需求质量检查

## 目标与责任

AI负责识别当前阶段、选择并应用合适技能、主动发现遗漏、提出建议、维护一致性及给出验证依据。用户负责提供真实业务信息和作出必要业务取舍，不承担提醒AI补齐专业产物的工作。

技能是方法来源；项目规则约束执行方式；交付证据用于核查结果。本文件定义质量检查，不扩展业务范围，不替代已确认决策、公共规范、模块需求和现有阶段门禁。

## 一、每次任务的工作步骤

1. **定位阶段**：读取Git变更和相关权威文档，明确本次目标、范围、已确认结论及尚缺证据。
2. **选择方法**：按下表读取主技能，需要时组合一种评审方法；遵循项目文档路由，不另造平行权威文档。
3. **主动判断**：指出影响当前目标的缺口及建议，不只照用户描述补文字；区分可直接完善的表达与需要业务决策的规则。
4. **完成产物**：对已授权范围直接推进，更新关联文档、图示和验收；需要决策时先准备可评估的具体方案，继续完成不依赖该决策的工作。
5. **核查交付**：对照相关质量维度检查，报告证据、剩余事项及推荐下一步。新证据或规则变化时重新检查，不重复执行无变化的检查。

| 工作阶段或问题 | 优先方法 | 要形成的判断 |
| --- | --- | --- |
| 发现问题与用户需求 | pm-product-discovery 的 interview-script、identify-assumptions、prioritize-assumptions、brainstorm-experiments 等对应技能 | 哪个问题值得做，证据是什么，如何便宜地验证 |
| 定位与范围取舍 | pm-product-strategy 的 product-strategy、value-proposition；必要时 pm-market-research | 为谁解决什么，边界和取舍是什么 |
| 需求细化与研发交接 | pm-execution 的 create-prd、user-stories、test-scenarios 按任务选择 | 流程、状态、数据、权限和验收是否足以实施 |
| 关键假设与方案评审 | pm-execution 的 strategy-red-team 或 pre-mortem | 什么事实会推翻方案，如何最小验证 |
| 成功指标与试点 | pm-data-analytics；指标定义采用 pm-marketing-growth:north-star-metric 或 pm-product-discovery:metrics-dashboard 按实际需要 | 用什么证据评价效果，不虚构基线或目标 |
| 实现审查与发布交接 | pm-ai-shipping 的 intended-vs-implemented、code-review、shipping-artifacts 按实际需要 | 需求是否落实、权限是否有效、哪些测试实际执行 |

技能名称由AI选择，用户无需手动触发。主技能模板不是完整性上限；例如PRD模板没有强制图示章节，仍须按复杂度表达数据、角色交接和异常路径。实现阶段的技术审查产物不得提前伪装为已有实现证据。

## 二、需求质量检查

以下维度按任务和阶段适用。可复用已有文档并链接证据，不要求每次生成所有产物；不适用项写明项目原因。结论使用“已覆盖／部分覆盖／缺失／不适用”，不能用文档存在代替内容检查。

| 维度 | 必须能回答的问题 | 主要证据位置 |
| --- | --- | --- |
| 用户与问题 | 谁遇到什么问题，事实、假设及优先级是什么？ | 产品发现、范围说明、PRD目标 |
| 价值与范围 | 为什么做、为何现在做、本期交付和外部边界是什么？ | 产品决策、产品总览、模块范围 |
| 业务架构与全局数据 | 系统由哪些业务能力组成，数据从哪里来，谁拥有权威状态，如何交接？ | 产品总览 |
| 模块流程与责任 | 角色如何交接，动作前置条件、成功结果和数据变化是什么？ | PRD、模块图示、最小配置 |
| 状态与异常 | 正常推进、等待、失败、取消、重试、跳过、终止、恢复各如何处理？ | 状态／异常图、决策、测试场景 |
| 数据与历史 | 对象如何关联，合并、版本、人员变更与替代记录如何保留证据？ | 模块对象关系、PRD数据规则 |
| 权限与治理 | 各动作的角色、范围、责任关系及状态门槛是什么，敏感操作如何治理？ | 公共规范、模块操作矩阵及拒绝场景 |
| 页面与交互 | 操作入口、关键按钮、空状态、等待、错误和确认反馈是否清楚？ | PRD交互、最小配置；需要时补原型 |
| 指标与验证 | 成功如何衡量，基线和目标来自哪里，验证假设需要什么最小证据？ | 指标基线、实验和试点记录 |
| 追踪与交付 | 决策、PRD、图、故事和场景是否一致，测试是已设计还是已执行？ | 需求追踪矩阵、执行结果 |

跨文档一致性检查应检索变更主题及旧说法，例如“待确认、自动淘汰、终面、CTO、权限、合并”。若旧记录保留用于追溯，应明确最新权威口径；当前导航和交付摘要不能继续把已确认规则写成待确认。

## 三、阶段结论与证据边界

- **需求可评审**：关键视图与规则已覆盖，未确认项显式列出，并给出建议、影响和验证方式。
- **需求可进入对应功能实施**：该功能所需关键业务决策已确认，验收可执行；未确认项不能以实现默认行为悄悄落地。局部缺口只影响对应功能，不自动阻断全部MVP。
- **功能已验收**：有真实执行结果及必要的日志／截图／测试证据；场景编号存在不代表通过。
- **可发布／可扩展**：满足既有发布门槛，具备必要的试点结果、责任人及未解决事项处置记录；不得因文档完善而宣称产品效果已验证。

重要阶段交付采用简短记录：本次主动发现什么、直接修复什么、哪项决策仍缺失、证据是什么、推荐下一步。链接可追溯到具体章节，避免泛泛“已检查”。

### 优先验证的三项判断

按影响与验证成本排序，未有数据支持时不编造概率或分数。

1. **合并规则足以实施**：保留主记录与旧证据能保证可追溯，这是已有方案的优点。但如果两条应聘记录分处面试中／待决策、或一条已淘汰，合并后的阶段和任务归属可能被研发自行推断。最小验证：用“待筛选＋待筛选、初筛＋面试中、淘汰＋待筛选”三组案例确认主记录阶段、活动任务、提醒及终止约束。判据：任一案例无法给出唯一预期，就不能将合并功能判定为可实施。推荐方案草案：先限制为均未进入流程的重复记录合并；已有流程记录只建立关联并保留独立流程。此建议改变现有合并范围，须业务确认后更新D-018相关规则；其他功能继续推进。
2. **关键异常能被一致理解**：明确图、规则和场景有助于交接；但文字分散仍可能使实现混淆。最小验证：研发／测试分别复述同场换人、新替代场次、前轮迟交不通过和CTO不参与四例，并给出状态、评价责任及待办预期。判据：解释与D-019不一致的具体链路先修正说明或规则，不能据“图已画好”判为通过。
3. **有指标方案就能证明价值**：已有最小指标且允许样本不足，设计合理；但未采集的基线不能证明效果。最小验证：按既有采集安排填写实际样本、时长与评价提交记录。判据：未取得足够可比样本时，只报告流程／权限验收结果，不据此扩大效率改善结论。影响试点效果判断，不阻塞已明确功能的开发。

上述下一步属于首次检查时点；D-020后不将双活动合并作为本期必需或整体阻塞，当前下一步为联合交接与技术评估，真实试点效果仍须证据。

### 图表样式与布局约定（2026-10-12）

- 图示颜色跟随阅读器的浅色／深色主题，不强制浅色背景或单独固定文字／连线颜色；阶段通过标题、说明与分段表达，不使用固定rect底纹。颜色不承担权限、成功或失败含义，结论必须写明。
- 数据和过程以自上而下为默认阅读方向，短关系图可左右展开；过宽数据流拆主业务与证据去向，跨多个阶段的角色时序拆段，并注明衔接前提。
- 操作／对象用矩形，条件分支用菱形；状态图及关系图使用各自标准符号和图例。实线／虚线按每张图说明解释，不能跨图假设统一含义：架构虚线为后续，时序虚线为反馈，ER连线为基数关联。
- 概念关系图显示中文业务对象及基数，不填技术类型、字段名或索引；箭头说明输入输出、条件或交接信息，权限仍引用权威矩阵。
- 阶段说明与角色命名一致，区分岗位身份、实际指派、系统动作和业务事件；无需把图型配置参数暴露为产品功能。
- 修改图示后分别检查浅色与深色实际渲染的文字、连线、标签碰撞与尺寸；语法通过及仅浅色检查不能替代深色视觉检查。不同Markdown阅读器可能采用不同缩放，宽图须支持放大阅读。

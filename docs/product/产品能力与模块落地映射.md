# 产品能力与模块落地映射

- **日期**：2026-10-10。
- **用途**：说明现有MVP能力由谁维护、在哪里操作、产出什么业务事实以及如何验收。不是新增模块、菜单承诺、数据库模型或接口契约。
- **状态**：现有需求的交接索引；下列待评审项不代表已确认业务规则。权威顺序沿用产品决策、公共规范、模块PRD、用户故事。

**新增基础缺口**：内部人员身份与账号关系尚未独立定义。下表的账号组织归属不代表人员管理需求完整；最小方案、确认路径与交付依赖见[项目规划](项目规划与阶段交付.md)。

## 一、信息所有权

| 层级 | 唯一维护内容 | 其他层如何使用 |
| --- | --- | --- |
| 产品探索 | 已确认业务决策、假设及范围变化原因 | PRD、公共规范、故事和验收按决策同步 |
| 公共规范 | 字段格式、附件安全、错误处理、授权模型、审计和生命周期共性规则 | 平台与招聘引用；不维护平行规则副本 |
| 平台基础能力 | 共用能力的职责与入口：账号、组织、字典、工作台、站内消息、审计／回收 | 承载公共机制；不决定候选人阶段、面试结果或录用 |
| 招聘管理 | 职位、应聘记录、邀约、轮次快照、场次、评价、决策及业务触发条件 | 提供经授权的业务事实、任务来源和业务动作；复用平台机制 |
| 总览与本映射 | 系统边界、能力依赖、阅读入口、交付归属 | 聚合引用，不复制完整字段和状态规则 |
| 用户故事与验收 | 用户目标、具体操作、可执行验证与追踪 | 验证权威规则，不反向新增权限或门槛 |

公共规范中已经存在招聘专用数量、轮次、时长和简历参数。本轮不迁移这些已确认参数；后续整理应保留一个权威维护位置，并更新引用及验收，不能平台和招聘各复制一份。公共安全机制与业务参数必须分别标明适用范围。

## 四、交付顺序与待评审项

1. **规则已明确的功能先评审拆分**：使用现有US／TS和上述归属；平台共用能力集中承载，招聘接入并验收业务准入。各行交接状态不能等同于实现已验收。
2. **字段补齐后再交接相应表单**：在招聘PRD C补来源标识的含义、输入方、必填性及渠道默认值；在D／E补计划开始、结束／时长、会议链接及实际完成时间的来源、必填与可修改性。公共文件只定义格式，不代替业务输入规则。
3. **聚合状态补齐后再交接相关工作台交互**：在PRD F定义逾期面试的时点、对象、解除条件和展示方式；如果需要通知，另明确收件人及频率。不要把M-003的评价逾期口径直接套为面试逾期。
4. **待办和消息单独验收**：推荐将未完成业务事项与消息未读分开显示，已读不自动完成业务；完成、终止、责任变更后按业务事实更新聚合与访问。该推荐需要交互评审，不能自行添加全局任务状态枚举或新提醒频率。
5. **交互与效果验证分别补齐**：平台及简单表单补文字操作基线即可，不强制高保真原型；M-004草案另作指标评审，不阻塞已确认招聘规则。

责任分工：产品负责补齐业务字段与分支、维护权威位置并准备推荐方案；业务负责人只确认仍有选择空间的业务政策；设计确认页面反馈和操作路径；研发设计共用能力及模块接入；测试按追踪矩阵执行并记录真实结果。不得要求研发凭字段名或“逾期”两字自行决定业务政策。

# pm-hrm 产品文档

本目录保存 pm-hrm 项目的产品探索、需求和决策产物。

本项目按用途分为两类：产品协作过程用于逐步形成版本共识；研发交付产物用于解释和实施已达成一致的产品。分类按信息用途组织，现有文件路径保持稳定，当前规则只维护一份。

## 一、产品协作过程：如何形成产品版本

**参与者**：业务负责人、产品经理与AI协作助手。**目标**：从业务诉求逐步明确问题、范围、规则和验收，形成一致的产品版本。

工作顺序：诉求与证据 → 分析缺口 → 推荐方案与影响 → 必要业务确认 → 记录决策 → 同步当前需求 → 版本复核。

- [产品探索与决策](产品探索/README.md)：诉求、背景证据、假设、候选方案、讨论与确认依据。
- [项目产品总览](产品总览.md)：项目聚合视图，汇总范围、进度、资料与交付入口。
- [TODO](TODO.md)、[项目规划与阶段交付](项目规划与阶段交付.md)：逐步确认和产出任务、当前进度、交接及排期安排。
- [产品经理工作与需求质量检查](产品经理工作与需求质量检查.md)、[可复用技能与项目接续](可复用技能与项目接续.md)：产出方法、质量检查与持续对齐。
- [对外输出产品需求文档格式模板](模板/对外输出产品需求文档格式模板.md)：按本期规范提供可复制的九章PRD、页面格式及交付包配套格式。
- 历史审查及旧提案保留当时记录，供追溯，不作为当前实施规则。

讨论过程可以完整保留。事实、建议、待确认和已确认结论须区分；未确认方案不进入研发正文作为执行要求。业务一致与产品版本形成后，维护下方交付产物。

研发正文表达已达成一致的产品，保留必要业务背景、当前规则、异常、交互、验收和真实依赖；候选方案、逐轮确认及AI工作过程留在第一类资料。当前待评估事项应明确影响及承担方，不将未确认建议写成确定功能。

## 两类资料的衔接与版本维护

- 业务确认后，产品更新决策依据，并同步PRD、字段、交互、图示及验收关联；研发直接阅读当前正文，必要时沿决策引用追溯。
- 交接须记录所用Git提交与相关文档版本，避免仅靠“最新版”称呼识别交付范围。
- 研发宣讲中的疑问先按现有规则澄清；确需改变业务范围或规则时，返回产品协作过程完成确认，再同步交付产物及变更影响。
- 版本记录置于文末，简述变更及研发影响，详细文本历史由Git追溯。交付文档、联合交接、功能验收和试点结果分别记录。

## 项目定位

pm-hrm 是面向 HRM 人资管理领域的 AI 产品管理与交付实践项目。项目通过 AI 辅助完成从产品发现到可验收交付的完整需求闭环。

HRM 是本项目实践的业务产品，整体规划包含工作台、招聘管理和绩效管理。

当前阶段只建设招聘管理模块 MVP，范围是从飞书职位发布完成后的职位建档，到候选人筛选、邀约、面试、评价和录用决策的完整闭环。工作台、账号、组织、权限和审计是本阶段的支撑能力；绩效管理暂不进入当前实现。

## AI 需求闭环

```text
产品发现 -> 假设验证 -> 需求澄清 -> PRD -> 用户故事
    -> 验收标准 -> 技术实现 -> 测试验证 -> 反馈迭代
```

AI 用于整理讨论、识别需求缺口、产出文档、拆解任务和辅助验证；业务负责人负责确认产品决策、权限边界和验收结果。

图示采用 Mermaid，与需求一起维护。全局业务架构及外部数据流归产品总览，模块内部流程、对象关系及异常分支归模块目录；PRD引用模块图示，不维护平行副本。箭头标注数据内容或流转条件，标明人工／系统动作、本期／后续边界，并关联决策与验收场景。图示变更随权威需求同步，不能用图示新增未经确认的业务规则；公共校验、权限和生命周期仍只引用公共规范。业务对象关系图不作为数据库模型或接口契约。

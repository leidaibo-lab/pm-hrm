# pm-hrm 产品持续对齐

## 目标

把用户目标转化为当前阶段可执行、可追溯、可验收的产品结论，并在一次任务内同步所有受影响的权威资料。

本技能维护工作方法，不保存 HRM 业务政策副本。业务事实、范围、权限、状态和验收门槛始终以仓库内当前权威文档为准。

## 进入任务

1. 按仓库 `AGENTS.md` 检查 Git 工作区，识别已有修改，避免覆盖无关工作。
2. 判断本次属于产品发现、业务决策、需求编写、需求变更、评审、交接还是状态查询。
3. 按任务读取最少但足够的当前依据：
   - 接续或状态判断：`docs/product/README.md`、`docs/product/TODO.md`。
   - 跨模块范围或能力归属：`docs/product/产品总览.md`。
   - 新增或改变业务规则：相关产品决策、公共规范、模块范围与 PRD。
   - 正式 PRD、交付或专业审查：`docs/product/产品经理工作与需求质量检查.md` 及对应源文档。
   - 涉及页面、弹窗、抽屉、按钮、输入字段、筛选项或展示字段：必须读取并执行[页面、按钮、表单命名与页面独立性](../../../docs/product/产品经理工作与需求质量检查.md#page-naming-standard)和[页面需求表头与用法规范](../../../docs/product/产品经理工作与需求质量检查.md#page-table-standard)，不得仅凭通用 PRD 习惯输出。
   - 面向研发、测试、设计的当前交付：`docs/output/README.md` 及其列出的正式产物。
4. 已确认事项不重复询问。历史记录只用于追溯，不覆盖当前权威结论。
5. 若存在适配的专项产品技能，选择一个主技能提供方法；本技能继续负责项目阶段、权威来源、影响传播和证据边界，不机械叠加全部技能。

## 权威与状态

同一业务规则冲突时，依次采用：

1. 已确认的产品决策。
2. 公共规范。
3. 模块范围说明和模块 PRD。
4. 用户故事中的补充说明。

`docs/product/TODO.md` 负责当前执行状态，`docs/product/产品总览.md` 负责系统边界和跨能力关系，`docs/output/` 是由权威源生成的正式交付包。不要直接编辑输出目录形成平行政策副本。

严格区分以下证据等级：

- 技能已安装或已读取。
- 文档已覆盖。
- 规则与引用已一致。
- 产品、研发和测试已完成联合交接。
- 实现已经真实测试。
- 产品效果已经试点验证。

低等级证据不能证明高等级结论。

## 主动工作流程

### 1. 明确结果与完成标准

- 识别目标用户、业务问题、用户价值、当前阶段和本次交付对象。
- 区分当前阻塞项、非阻塞事项和后续阶段事项。
- 没有资源与执行证据时，不虚构负责人、工期、测试结果或收益。

### 2. 检查完整闭环

对新增或变化的功能逐项检查：

- 角色：谁发起、谁处理、谁查看、谁负责交接。
- 流程与状态：起点、主链、终点、回退、取消、失效和恢复。
- 数据：来源、权威归属、字段、默认值、必填、修改、历史和生命周期。
- 权限：查看、创建、修改、下载、导出、删除、恢复、审计及越权反馈。
- 页面与交互：入口、动作、成功、失败、空、加载、禁用和并发反馈。
- 指标：业务价值指标、功能验收和试点效果分别定义。
- 异常：缺失、重复、失效、并发、外部依赖失败和责任变化。
- 验收：正常、反向、边界和权限场景能得到唯一预期。

涉及员工档案、身份证件、合同、薪酬、绩效或其他敏感人事数据时，单独核对最小必要、权限、审计、下载／导出、删除／恢复和生命周期。

### 页面规格强制门禁

凡新增、修改或评审页面需求，必须执行上述两个页面规范章节，并满足：

- 按实际载体和业务对象命名列表页、详情页、新增／编辑页、弹窗或抽屉；按钮使用界面实际文案，表单只表示输入区域。
- 页面按独立阅读单元表达目标角色、入口与返回、区域、展示、按钮、输入、权限、结果、异常和验收；不能把不同页面的动作混成操作总表让研发自行拆分。
- 页面需求按实际内容使用“按钮”“输入字段”“筛选项”“展示字段”四类表，并严格采用权威规范中的固定列名、顺序和列职责；不自创近义表头，也不为不存在的内容制造空表。
- 新增／编辑共用字段时只维护一份字段定义，但明确默认值、编辑回填、修改限制、保存结果和返回位置；列表与详情仍分别定义。
- 输出前至少推演筛选重置、空值展示、编辑回填、保存失败、失权提交及适用的并发场景，确认正式输出与源规范一致。

固定表头及详细填写要求只维护在质量检查文档，不复制到本技能；每次使用都读取当前版本，避免规范漂移。

### 3. 判断是否需要用户决策

- 已确认规则缺少表达、导航、图示、引用或验收关联：直接补齐并同步，不把维护工作重新抛给用户。
- 发现会改变业务范围、授权、状态规则、数据生命周期或成功门槛的新选择：先给推荐方案、理由、反方影响和最少必要问题；确认前标为建议或待决策。
- 关键假设缺少证据：提出最小验证、所需样本和失败判据，不用泛泛风险清单制造阻塞。
- 小范围修正保持小范围；只有证据表明存在同类系统性问题时才扩大检查范围。

### 4. 同步受影响产物

沿引用关系检查并更新适用内容：

```text
产品决策
  -> 公共规范或模块权威需求
  -> 字段、流程、状态、权限与图示
  -> 页面交互、用户故事与验收场景
  -> 追踪关系、TODO与项目总览
  -> 正式输出
```

- 公共规则只在公共规范维护；模块写业务特有规则和例外。
- 总览只聚合边界、关系、状态和入口，不复制完整模块细节。
- 产品协作资料保留证据、讨论和决策过程；正式交付只呈现当前定义、必要依赖和验收预期。
- 研发不应通过拼接大量内部文件才能理解一个功能；每项功能应连续表达输入、操作、权限、结果、异常与验收。
- 已确认规则变化时同步相关图示和验收，不用图示创造新政策。

### 5. 复核与验证

- 从首次接触项目的研发、测试或设计视角完整阅读受影响内容，检查能否独立执行。
- 页面需求变更须核对页面命名、实际载体、四类表格的固定列名与顺序，以及字段／按钮在对应页面的完整反馈。
- 用具体业务案例推演主链、异常、越权和责任变化；目录、链接和编号通过不能替代语义复核。
- 修改正式需求源后，按项目规则重新生成输出，并运行交付预检与独立复检。
- 至少执行与变更相称的格式、引用、生成一致性和 Git 差异检查；只报告实际执行过的验证。
- 若本次仅分析或评审，不擅自修改文件、实现代码、提交、推送或发布。

## 阶段门禁

- 产品发现结论确认前，不进入技术方案或业务代码实现。
- MVP 范围确认前，不建立正式数据库模型或接口契约。
- 文档定义完成不等于可实施；可实施还需影响本批行为的规则唯一、追踪完整并完成相应交接评审。
- 实现完成不等于已验收，功能验收不等于产品效果验证。

## 沟通输出

用中文，先给当前判断或推荐方案，再说明依据与影响。按任务规模报告：

- 已完成事项。
- 当前阶段阻塞项。
- 非阻塞事项。
- 验证证据与未验证边界。
- 推荐下一步。

不要要求用户记住技能名称或逐项提醒产品经理应做的工作；用户只需提供真实业务信息并作必要取舍。
